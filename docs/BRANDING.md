# AndersXn OS branding

Everything visual traces back to two files in `branding/`:

- `assets/AXnobg.png` - the master mark, 2000x2000 with alpha
- `ascii/axos-logo-master.txt` - the 100-column ASCII export of it

## The ASCII marks

Three sizes are generated from the master by
`branding/ascii/generate-variants.py`, plus one pre-coloured copy produced at
build time:

| File | Size | Used by |
|---|---|---|
| `axos-logo.txt` | 74x31 | `/etc/motd`, `ax-installer --logo` |
| `axos-logo-compact.txt` | 37x16 | `/etc/issue`, `ax-release` |
| `axos-logo-compact.ansi` | 37x16 | Fastfetch (generated by stage 30) |
| `axos-logo-mini.txt` | 25x11 | narrow terminals - the TUI header falls back to it |

Regenerate after re-exporting the master:

```bash
make ascii     # regenerates, and syncs the copies the installer embeds
```

The downsampler collapses NxM blocks of the master and inks a cell when the
block contains any ink at all, drawing in `$` - the glyph the master itself is
drawn in. A proportional density ramp was tried first and rejected: the mark is
sparse outline-and-fill line art, and shading broke thin strokes into dotted
noise. Solid two-tone keeps the silhouette readable down to 25 columns.

**Pick the largest variant that fits.** `/etc/issue` originally used the 25-column
mini variant and the mountain was unrecognisable; at 37 columns the silhouette
survives, and the whole banner still fits an 80x25 console with the login prompt
below it. The full 74-column mark fits an 80-column terminal, so `motd` - which
prints on its own with nothing beside it - uses that.

## Why Fastfetch gets its own file

Fastfetch's `file` logo type treats `$` as a colour-placeholder prefix and
consumes characters. This mark is almost entirely `$`, so it renders as
shredded nonsense. `file-raw` prints the bytes verbatim - but then applies no
colour of its own.

So stage 30 generates `axos-logo-compact.ansi`: the same art with the accent
colour baked in as ANSI escapes. `axos-logo-compact.txt` remains the single
source of the shape; the `.ansi` file is derived from it on every build.

## The palette

Only the mark itself was supplied as a brand asset, so the accent tones were
derived from it: a snow-white alpine glyph over deep space.

| Token | Hex | Role |
|---|---|---|
| Ink | `#0B0E14` | base background |
| Surface | `#131722` | panels, raised surfaces |
| Snow | `#F2F5FA` | primary foreground - the logo white |
| Accent | `#4FC3F7` | glacier cyan, primary accent |
| Accent deep | `#1B6CA8` | unfocused / pressed accent |
| Muted | `#6B7A90` | secondary text |
| OK / Warn / Error | `#63D68A` `#E8B84B` `#E5484D` | status |

Three files declare the palette as named tokens:

- `build/lib/common.sh` - the shell side, `AXOS_HEX_*`
- `installer/internal/branding/branding.go` - the Go side
- `installer/gui/ax-installer-gtk` - the GTK front end

**A dozen more hardcode the hex values directly** - Plymouth's script, the
Limine palettes, the zsh prompt, the Plasma `kdeglobals`, the btop theme, the
motd colours. That is a real wart: there is no single constant to change.
Changing the brand accent means finding all of them:

```bash
grep -rln '4FC3F7\|4fc3f7\|79,195,247\|79;195;247' build branding installer provisioning
```

Fifteen files at the time of writing. Any rework of the palette should start by
collapsing that.

## KDE Plasma

Plasma is themed with Breeze Dark plus the AndersXn accent, set system-wide in
`/etc/xdg/kdeglobals` so the live session, the greeter and every account the
installer creates inherit it without a per-user setup step. Plasma 6 reads
`AccentColor` from there.

The wallpaper is defaulted through `/etc/skel`, which is what every account
AX-Installer creates is built from. The SDDM greeter background is set in
`theme.conf.user` rather than by editing the packaged Breeze theme, so it
survives that theme's updates.

## Raster assets

Stage 30 derives every raster the system needs from the single master PNG using
ImageMagick:

- `logo.png` - 512px, alpha preserved, for Plymouth
- `splash.png` - 1920x1080, mark composited on ink, for the bootloader
- `bar-bg.png` / `bar-fg.png` - 1x3 slivers the Plymouth script scales
- wallpapers at 1920x1080, 2560x1440 and 3840x2160

If ImageMagick is absent the build warns and installs the master unscaled rather
than failing: a slightly wrong splash beats no image at all.

## The guard against silent breakage

Rendered files are checked for leftover `@TOKEN@` placeholders before the build
continues (`assert_rendered` in stage 30). This exists because a template token
and the stage feeding it drifted apart twice, the render silently no-opped, and
a literal `@ASCII_COMPACT@` shipped on the login screen. Cheap to check,
embarrassing to miss.
